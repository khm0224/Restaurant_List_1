인사와 서비스 한 줄 소개

저희 팀은 김진헌 팀장과 저, 그리고 박성훈, 구광모 네 명으로 구성되어 있습니다.

저희가 만든 서비스는 춘천의 맛집을 동네 단위로 정리하고, 지도 위에서 바로 찾아볼 수 있게 만든 웹 서비스 봄내로그입니다. '봄내'는 춘천의 옛 이름이고, 여기에 기록이라는 뜻의 '로그'를 붙였습니다.

오늘은 서비스 구조와 주요 기능을 화면 순서대로 설명드리고, 이어서 실제 시연을 보여드린 뒤 질문을 받겠습니다.

확인발표자를 김형민으로 바꾸셔서 팀원 명단을 박성훈으로 고쳤습니다. 발표자가 박성훈이면 이 줄을 김형민으로 되돌리세요.

0:45p3 사이트맵

전체 구조 · 기술 스택 선언

먼저 전체 구조입니다. 메인 화면을 중심으로 다섯 갈래로 나뉩니다. 로그인과 회원가입, 서비스 소개와 소식·공지사항, 메인 지도, 지역 선택을 거친 맛집 탐색, 그리고 마이페이지입니다.

여기서 한 가지 봐주실 점은, 메인 지도와 맛집 탐색, 마이페이지 이 세 경로가 모두 식당 상세 정보라는 한 화면으로 모인다는 것입니다. 사용자가 어느 경로로 들어오든 도착지는 같습니다. 그래서 상세 페이지에 식당 데이터를 넘기는 방식을 한 가지로 통일했고, 이 부분은 상세 페이지 설명에서 다시 말씀드리겠습니다.

기술 스택은 HTML, CSS, 순수 자바스크립트입니다. 프레임워크와 서버를 사용하지 않았고, 데이터는 브라우저 저장소에 보관합니다. 이 선택이 앞으로 설명드릴 구현 방식의 대부분을 결정했습니다.

복선마지막 문장이 이 발표에서 가장 중요한 한 줄입니다. "서버가 없다"를 여기서 선언해두면, 뒤에 나오는 쿠키·localStorage·하드코딩된 관리자 아이디가 "이상한 선택"이 아니라 "제약에 대한 대응"으로 읽힙니다.

2:00p5 header

헤더 — 공통 컴포넌트

헤더 영역입니다. 왼쪽은 로고, 가운데는 메뉴, 오른쪽은 검색창과 로그인 버튼으로 구성했습니다.

헤더는 12개 페이지에서 똑같이 쓰입니다. 페이지마다 복사해 두면 메뉴 하나를 고칠 때 12개 파일을 전부 고쳐야 하고, 한 곳을 빠뜨리면 페이지마다 헤더가 달라집니다. 그래서 헤더를 별도 HTML 파일로 분리하고, fetch로 불러와 각 페이지에 삽입하는 방식으로 만들었습니다.

그리고 fetch로 가져올 때 페이지마다 폴더가 위치한 곳이 달라서 같은 링크라도 경로가 달라집니다. 그래서 헤더를 삽입한 직후에 링크 경로를 다시 계산해 주는 처리를 넣었습니다.

예상 질문 B-1 · B-5"서버가 있으면 어떻게 하나요?" → "컴포넌트나 템플릿 엔진이 그 역할을 합니다." 경로 재계산을 더 물으면 new URL(상대경로, 헤더파일주소)로 절대 주소를 만든다고 답하세요.

2:35p7 통합 검색

통합 검색 · 자동완성

다음은 식당명, 업종, 지역 세 가지를 입력창 하나에서 받는 통합 검색입니다.

로직은 input 이벤트로 타이핑을 실시간으로 감지하고, includes로 부분 일치를 확인한 뒤, slice로 최대 여덟 개까지만 잘라서 보여줍니다. 결과를 전부 띄우면 목록이 화면을 덮어버리기 때문입니다.

입력한 값이 지역이나 업종이면 목록 페이지로, 특정 식당이면 상세 페이지로 보냅니다. 이때 검색 조건은 URLSearchParams로 주소창에 담아서 넘깁니다. 그래서 주소를 그대로 복사해 붙여넣어도 같은 결과가 다시 열립니다.

예상 질문 A-7"검색은 URL, 식당 선택은 sessionStorage인데 왜 다른가요?" → 공유 가능성이 기준. 검색 조건은 주소 복사로 재현돼야 하고, 클릭한 식당 하나는 그럴 필요가 없습니다.
3:05p8 heroslider

대표 맛집 슬라이더

메인 상단의 대표 맛집 슬라이더입니다. 리뷰 수를 기준으로 정렬한 상위 다섯 곳을 보여줍니다.

3:55p10 지도·순위

주변 맛집 지도와 TOP 3

메인 하단입니다. 왼쪽이 지도, 오른쪽이 맛집 순위입니다.

지도는 Google Maps API로 그렸고, 선택한 지역의 맛집 위치를 마커로 찍습니다. 여기서 한 가지 처리한 것은, 구글 지도가 기본으로 보여주는 상점 마커를 전부 껐다는 점입니다. 저희 목록에 있는 식당만 보여야 화면이 정리되기 때문입니다.

오른쪽 순위는 탭이 두 개입니다. 지역별 맛집은 선택한 동의 상위 세 곳을 보여주고, 내 주변 맛집은 사용자의 현재 위치를 기준으로 반경 안의 식당을 가까운 순으로 세 곳 보여줍니다. 반경은 250미터, 500미터, 1킬로미터, 그리고 직접 설정 중에서 고를 수 있고, 각 카드에 실제 거리를 함께 표시합니다.

거리 계산은 Haversine 공식을 직접 구현했습니다. 위도와 경도는 평면 좌표가 아니라 구면 좌표라서, 피타고라스 정리로 계산하면 오차가 생깁니다. Haversine은 지구를 구로 두고 두 점 사이의 최단 거리를 구하는 공식입니다.

예상 질문 F-2 · 1순위공식을 외울 필요는 없고 "왜 피타고라스가 아닌가"만 명확하면 됩니다. 경도 1도의 실제 거리가 위도에 따라 달라져서 cos(위도)로 보정한다고 답하세요. 파일은 js/nearbyRestaurantService.js, 지구 반지름 상수 6371.0088km.

5:25p13 Map Area

지도 — 적용 기술 네 가지

지도 영역입니다. 이 화면은 메인 페이지와 달리 Kakao Maps JavaScript API를 사용했습니다.

적용한 기술을 순서대로 말씀드리겠습니다. 첫째, 식당 좌표는 CSV 파일로 관리하고 fetch로 읽어와 SVG 마커로 변환해 찍습니다. 기본 마커 대신 SVG를 쓴 이유는 마커의 색과 모양을 서비스 톤에 맞추기 위해서입니다.

둘째, 행정구역 경계선은 GeoJSON 데이터를 폴리곤으로 그립니다. 화면에서 붉은 선으로 보이는 부분입니다.

셋째, 현재 위치는 브라우저의 Geolocation API로 받아옵니다.

넷째, 길찾기 경로는 Kakao Mobility Directions API를 호출해서 받은 좌표들을 Polyline으로 이어 그립니다.

예상 질문 F-1 · 최상위"메인은 구글, 여기는 카카오인데 왜 섞었나요?" — 변명하지 말고 이유와 개선안을 같이. 길찾기가 Kakao Mobility라서 지도도 맞췄고, 다시 만든다면 Kakao로 통일하겠다고 답하세요.

6:15p15 내 위치

현재 위치 표시

(내 위치 버튼을 가리키며) 이 버튼은 '내 위치'를 보여주는 버튼입니다. 누르면 Geolocation API로 GPS 좌표를 요청하고, 받아온 좌표에 현재 위치 마커를 찍습니다.

여기서 한 가지 처리한 부분이 있습니다. Geolocation API는 결과를 콜백으로 돌려주는 방식이라, 그대로 쓰면 이후 코드가 콜백 안으로 계속 들어가게 됩니다. 그래서 Promise로 한 번 감싸서 async / await로 쓸 수 있게 만들었습니다. 또 위치 조회는 실패하는 경우가 많아 권한 거부, 위치 확인 실패, 시간 초과 세 가지를 나눠서 각각 다른 안내 문구를 띄우도록 했습니다.

코드 근거js/geolocationService.js — 옵션은 enableHighAccuracy: true, timeout: 10000, maximumAge: 0.

정규식 질문 대비(?=.*[a-zA-Z])는 전방 탐색이라 자리를 소비하지 않고 "어딘가에 하나는 있다"만 확인, 그래서 입력 순서가 자유롭다고 답하세요. 특수문자를 "영문·숫자가 아닌 것"으로 안 잡은 이유(한글·공백까지 통과)도 함께.

성공하면 로그인한 사용자의 아이디를 쿠키에 하루 동안 저장합니다. 회원 목록은 localStorage에 두면서 로그인 상태만 쿠키로 나눈 이유는 localStorage에는 만료라는 개념이 없기에, date만 설정하면 되는 쿠키로 로그인 유지를 관리하고 있습니다.

그리고 쿠키에는 아이디만 넣습니다. 이름이나 사진까지 쿠키에 담으면, 사용자가 개인정보를 수정했을 때 쿠키의 값과 저장소의 값이 서로 일치하지 않는 일이 발생합니다. 그래서 쿠키에는 누구인지만 두고, 나머지 정보는 그때그때 조회합니다. 현재 사용자를 판단하는 기준은 getCurrentUser 함수 하나뿐입니다.

마지막으로 로그인이 성공하는 순간 헤더의 로그인 버튼, 프로필 메뉴, 즐겨찾기 별 표시처럼 화면 여러 곳이 동시에 갱신되어야 하는데 이걸 로그인을 구현한 코드에서 다 구현하면 화면이 하나 늘어날 때마다 로그인 코드를 수정해야 합니다.

그래서 auth:changed라는 커스텀 이벤트를 만들었습니다. 로그인 코드는 상태가 바뀌었다고 알리기만 하고, 각 화면이 이 이벤트를 구독해서 스스로 다시 그립니다. 즉, 화면이 늘어나도 로그인 코드는 고치지 않습니다.

여기서 멈추고 눈 마주치기발표 전체에서 가장 설계다운 부분입니다. 천천히 말하세요. 질문이 들어오면 "React의 Context가 하는 일을 수동으로 구현한 셈입니다"가 좋은 마무리 문장입니다.

A. 프로젝트 전반 · 설계 8문항

프로젝트를 한 문장으로 소개해 보세요.

춘천 맛집을 동네별·위치 기반으로 검색하고 리뷰와 즐겨찾기를 관리하는 웹 서비스입니다. 서버 없이 브라우저 저장소만으로 구현해서, 원래 서버가 담당할 인증·검증·데이터 관리를 클라이언트에서 처리한 것이 특징입니다.

왜 서버 없이 만들었나요?

수업 범위가 프론트엔드였기 때문에 서버와 DB 없이 구현했습니다. 그래서 원래 서버가 담당할 인증, 검증, 데이터 관리를 브라우저가 대신 하고 있습니다. 이상해 보이는 코드는 대부분 이 제약 때문입니다.

서버가 있었다면 어떤 부분이 가장 크게 바뀌나요?

세 가지입니다. 회원 정보가 localStorage에서 DB 테이블로, 로그인 상태가 쿠키의 아이디에서 세션이나 JWT 토큰으로, 검증이 클라이언트 단독에서 클라이언트와 서버 양쪽으로 바뀝니다.

파일 구조를 어떻게 나눴나요?

세 계층입니다. 인증 계층(auth.js, login.js), 저장소 계층(board.js, favorites.js), 데이터 계층(restaurantData.js, restaurantService.js, 위치 서비스들). 그 위에 화면별 스크립트가 있습니다.

계층을 나눌 때 지킨 원칙이 있나요?

단방향 의존입니다. 화면 스크립트는 저장소를 부르지만, 저장소는 어느 화면이 자기를 쓰는지 모릅니다. auth.js는 DOM을 전혀 건드리지 않아서 순수 로직으로만 되어 있습니다.

아래층이 위층을 알기 시작하면 코드가 순식간에 엉킵니다.

전역 변수(window.Board 등)를 쓴 이유는?

모듈 번들러 없이 script 태그로만 불러오는 구조라 파일 간에 값을 넘길 방법이 전역밖에 없었습니다. 대신 아무거나 전역에 두지 않고 각 파일이 공개할 것만 객체 하나에 묶어서 내보냈습니다. 실무라면 ES Module의 import/export를 씁니다.

검색은 URL로, 식당 선택은 sessionStorage로 넘기던데 왜 다른가요?

공유 가능성이 기준이었습니다. 검색 조건은 주소를 복사해 다시 열 수 있어야 해서 URLSearchParams로 URL에 담았고, 클릭한 식당 하나는 그럴 필요가 없는 일회성 데이터라 sessionStorage에 담았습니다.

기능이 많은데 우선순위는 어떻게 정했나요?

사용자가 도착하는 화면을 기준으로 잡았습니다. 어느 경로로 들어와도 결국 식당 상세 페이지로 모이기 때문에, 상세 페이지와 그곳으로 데이터를 넘기는 방식을 먼저 확정한 뒤 나머지 화면을 붙였습니다.

B. 구조 · 컴포넌트 · 이벤트 9문항

헤더를 왜 fetch로 불러오나요?

12개 페이지가 같은 헤더를 쓰는데, 복사해 두면 메뉴 하나 고칠 때 12곳을 전부 고쳐야 하고 한 곳만 빠뜨려도 페이지마다 헤더가 달라집니다.

서버가 있으면 Thymeleaf의 th:replace나 React 컴포넌트가 이 일을 대신합니다. fetch는 그걸 수동으로 구현한 것입니다.

헤더 경로를 왜 HTML의 data 속성으로 넘겼나요?

페이지마다 헤더 파일까지의 상대 경로가 다릅니다. 경로를 JS에 하드코딩하면 페이지마다 다른 JS가 필요해집니다. 그래서 HTML이 JS에게 경로를 알려주는 방식으로 data-header-component 속성을 쓰고, JS는 document.currentScript로 자기 script 태그를 찾아 그 값을 읽습니다.

document.currentScript를 왜 최상위에서 잡아두나요?

currentScript는 그 스크립트가 실행되는 순간에만 유효합니다. DOMContentLoaded 콜백 안에서 읽으면 이미 null이라서, 파일 맨 위에서 변수에 담아둡니다.

dataset을 쓸 때 주의할 점이 있나요?

dataset 값은 항상 문자열입니다. 리뷰와 댓글 id는 숫자라서 Number()로 변환하지 않으면 "123" === 123이 false가 되어 삭제가 조용히 실패합니다. 에러도 안 나서 찾기 가장 어려운 종류의 버그입니다.

삽입한 헤더의 링크 경로는 어떻게 처리했나요?

fetch로 가져온 HTML을 innerHTML로 넣으면 링크가 삽입된 페이지 기준으로 해석돼서 깊은 폴더에서는 404가 납니다. 그래서 헤더 HTML은 링크를 data-header-link에 담아두고, JS가 new URL(상대경로, 헤더파일주소)로 절대 주소를 만들어 href에 넣습니다.

이벤트 위임이 뭔가요? 왜 필요했나요?

각 요소에 리스너를 붙이는 대신 부모나 document에 하나만 걸고, 클릭된 위치를 확인해 처리하는 방식입니다.

두 가지 이유로 필요했습니다. 헤더가 fetch로 늦게 오기 때문에 로그인 버튼이 아직 없을 때 리스너를 붙이면 null 에러가 납니다. 그리고 innerHTML로 목록을 다시 그리면 기존 리스너가 전부 사라지는데 위임이면 살아남습니다.

event.target과 currentTarget의 차이는?

target은 실제로 클릭된 가장 안쪽 요소이고, currentTarget은 리스너가 붙어 있는 요소입니다. 버튼 안에 아이콘이 있으면 target은 img가 되기 때문에, closest()로 위로 올라가며 원하는 요소를 찾아야 안전합니다.

stopPropagation을 안 쓰고 closest를 쓴 이유는?

stopPropagation은 이벤트가 위로 올라가는 걸 막아서, 나중에 document에 붙는 다른 기능이 그 영역에서만 조용히 동작하지 않게 됩니다. 에러도 안 나서 원인을 찾기 극도로 어렵습니다. 그래서 이벤트를 끊는 대신 클릭 위치를 확인하는 방식으로 처리했습니다.

헤더 로드 후 초기화 순서가 왜 중요한가요?

헤더 HTML을 넣고 → 프로필 메뉴를 조립하고(구독 등록) → 그다음에 상태를 반영해야 합니다. 순서를 바꿔서 상태 반영이 먼저 실행되면 아직 아무도 구독하지 않아서 이벤트가 허공에 흩어지고, 헤더가 로그인 상태를 반영하지 못합니다.

C. 인증 · 상태 관리 10문항

로그인 상태를 왜 쿠키에 저장했나요?

만료 시간 때문입니다. localStorage에는 만료 개념이 없어서 한 번 로그인하면 지울 때까지 계속 로그인 상태로 남습니다. 쿠키는 만료일을 직접 지정할 수 있어서 하루로 설정했습니다.

반대로 회원 목록은 왜 localStorage인가요?

세 가지입니다. 쿠키는 약 4KB 제한이 있어 프로필 사진이 들어가면 다섯 명도 못 담습니다. 쿠키는 모든 HTTP 요청에 자동으로 실려 나가는데 회원 목록을 서버로 보낼 이유가 없습니다. 그리고 값에 세미콜론이 들어가면 쿠키 파싱이 깨지는 문제도 있었습니다.

쿠키에 이름이나 사진은 왜 안 넣었나요?

같은 정보를 두 곳에 두면 어긋나기 때문입니다. 개인정보를 수정하면 저장소의 이름은 바뀌는데 쿠키의 이름은 그대로 남습니다. 그래서 쿠키에는 누구인지만 두고 나머지는 getCurrentUser()가 그 아이디로 조회합니다.

getCurrentUser()는 무엇을 반환하나요?

쿠키에 아이디가 없으면 null, 있으면 그 아이디로 회원 목록에서 찾은 회원 객체를 반환합니다. 회원을 못 찾아도 null입니다. 로그인 여부의 판단 기준이 코드 전체에서 이 함수 하나뿐입니다.

쿠키 삭제는 어떻게 하나요?

쿠키에는 삭제 명령이 없습니다. 만료일을 1970년으로 지정하면 브라우저가 알아서 버립니다. 트릭이 아니라 표준적인 방식이고 실무에서도 똑같이 합니다.

encodeURIComponent와 path=/ 는 왜 필요한가요?

encodeURIComponent는 값에 세미콜론이나 등호, 한글이 들어가면 쿠키 형식이 깨지기 때문에 안전한 문자로 바꿔줍니다. path=/는 사이트 전체에서 쓰겠다는 뜻인데, 빼면 현재 폴더에서만 유효해서 html/auth에서 만든 쿠키를 index.html이 못 읽습니다.

로그인하면 화면 여러 곳이 동시에 바뀌는데 어떻게 처리했나요?

auth:changed라는 커스텀 이벤트로 발행–구독 구조를 만들었습니다. 로그인 코드는 상태가 바뀌었다고 알리기만 하고, 헤더·프로필 메뉴·즐겨찾기 표시가 각자 구독해서 스스로 다시 그립니다.

화면이 늘어나도 로그인 코드는 고치지 않습니다. React의 Context가 하는 일을 수동으로 구현한 셈입니다.

auth:changed의 구독자는 누구누구인가요?

헤더의 로그인 버튼, 프로필 드롭다운 메뉴, 즐겨찾기 별 표시, 그리고 페이지별 화면 스크립트입니다. 발행하는 쪽은 로그인, 로그아웃, 개인정보 수정, 페이지 진입 네 곳이고 전부 refreshAuthUI 하나를 거칩니다.

구독 등록 후에 그 함수를 한 번 더 직접 호출하는 이유는?

이벤트는 앞으로 일어날 변화만 알려주기 때문입니다. 페이지에 처음 들어온 시점에는 아직 아무 이벤트도 발생하지 않아서, 초기 상태를 그리려면 직접 한 번 불러야 합니다.

로그인 실패 메시지를 왜 하나로 통일했나요?

"아이디가 없습니다"와 "비밀번호가 틀렸습니다"를 구분하면, 아이디만 바꿔가며 시도해서 어떤 계정이 존재하는지 알아낼 수 있습니다. 회원가입에서 관리자 아이디를 입력했을 때도 같은 이유로 "이미 사용 중인 아이디입니다" 하나로 처리했습니다.

D. 데이터 저장 10문항

데이터가 어디에 저장되는지 전부 말해 보세요.

네 곳입니다. 쿠키에 로그인한 사람의 아이디, localStorage에 회원 목록·댓글·리뷰, sessionStorage에 목록에서 클릭한 식당 정보, 그리고 코드 안에 식당 199곳 데이터와 좌표 CSV가 읽기 전용으로 있습니다.

localStorage와 sessionStorage의 차이는?

localStorage는 지울 때까지 남고 sessionStorage는 탭을 닫으면 사라집니다. 그래서 회원 정보처럼 계속 남아야 하는 건 localStorage, 목록에서 상세로 넘기는 일회성 데이터는 sessionStorage에 담았습니다.

localStorage에 객체를 어떻게 저장하나요?

localStorage는 문자열만 저장할 수 있어서 JSON.stringify로 바꿔 넣고, 읽을 때 JSON.parse로 되돌립니다.

저장된 값이 깨져 있으면 어떻게 되나요?

JSON.parse가 예외를 던지기 때문에 try/catch로 감싸고, 실패하면 빈 배열로 시작합니다.

한 가지 더 처리한 게 있는데, JSON.parse는 배열이 아닌 값도 통과시킵니다. 그래서 Array.isArray로 한 번 더 확인합니다. 배열이 아니면 이후 find 같은 메서드가 전부 터집니다.

식당 ID를 왜 문자열 조합으로 만들었나요?

DB가 없어서 자동 증가 기본키를 쓸 수 없었습니다. 대신 데이터 안에서 유일하게 식별되는 값들을 조합했고, 이 키 하나에 리뷰·댓글·즐겨찾기가 전부 묶여 있습니다.

그 키 방식의 문제점은 무엇인가요?

배열 순서가 바뀌면 기존 데이터가 다른 식당을 가리키게 됩니다. 그래서 키를 만들고 쪼개는 코드를 board.js 한 곳으로 모았습니다. 예전에 형식이 두 조각에서 세 조각으로 바뀌었을 때, 쪼개는 쪽이 에러 없이 잘못된 값을 내놓은 적이 있었기 때문입니다.

예전 형식 키는 어떻게 처리하나요?

파싱할 때 조각 수를 세서, 세 조각이면 새 형식으로 읽고 두 조각이면 옛 형식으로 읽습니다. 카테고리가 한식·일식·중식·양식·디저트뿐이라 이름에 밑줄이 없어서 이 판별이 성립합니다.

댓글에 작성자 이름 대신 아이디를 저장한 이유는?

이름은 개인정보 변경으로 바뀔 수 있기 때문입니다. 이름을 저장하면 예전 글에 옛날 이름이 계속 남습니다. 아이디로 저장해 두고 화면에 보여줄 때 현재 이름을 조회합니다.

DB로 치면 외래키로 참조하고 이름은 조인해서 가져오는 것과 같은 발상입니다.

localStorage를 직접 쓰지 않고 왜 Board 객체로 감쌌나요?

저장소 키가 여러 파일로 퍼지는 걸 막기 위해서입니다. 키 이름이 두 곳에 있으면 저장 구조를 바꿀 때 한 곳만 고치게 되고, 그러면 에러 없이 빈 배열만 돌려주며 조용히 깨집니다. 지금은 함수로만 접근하기 때문에 나중에 서버 API로 바꿔도 이 파일 하나만 고치면 됩니다.

즐겨찾기 저장 실패 시 롤백이 무슨 뜻인가요?

프로필 사진 때문에 용량 한도를 넘으면 setItem이 예외를 던지고 아무것도 저장하지 않습니다. 그런데 메모리의 배열은 이미 바뀐 상태라 화면에는 별이 켜지고 저장은 안 된 상태가 됩니다. 그래서 저장에 실패하면 배열도 원래대로 되돌립니다.

toggleFavorite은 추가면 true, 해제면 false, 비로그인이나 저장 실패면 null 세 가지를 반환합니다.

E. 화면 렌더링 · 성능 7문항

화면을 그리는 방식이 두 가지던데 왜 섞여 있나요?

innerHTML에 템플릿 리터럴을 넣는 방식과 createElement로 만드는 방식을 씁니다. 앞쪽은 짧고 HTML 모양이 눈에 보여서 목록에 썼고, 뒤쪽은 XSS를 원천 차단하고 이벤트를 바로 연결할 수 있어서 사용자 정보를 표시하는 곳에 썼습니다.

innerHTML로 다시 그리면 어떤 문제가 생기나요?

기존 요소가 통째로 교체되기 때문에 거기 붙어 있던 이벤트 리스너가 전부 사라집니다. 그래서 innerHTML로 그리는 화면은 이벤트 위임을 반드시 같이 써야 합니다.

map().join('') 에서 join의 빈 문자열이 왜 필요한가요?

배열을 그냥 문자열로 만들면 요소 사이에 쉼표가 끼어들어 화면에 쉼표가 그대로 보입니다. join('')으로 이어 붙여야 깔끔한 HTML 문자열이 됩니다.

DocumentFragment를 왜 썼나요?

카드를 하나씩 화면에 붙이면 붙일 때마다 브라우저가 레이아웃을 다시 계산합니다. DocumentFragment는 화면에 없는 가상 컨테이너라서 여기에 다 조립한 뒤 한 번에 붙이면 계산이 한 번만 일어납니다.

페이지네이션은 어떻게 구현했나요?

데이터를 전부 가져와서 slice로 현재 페이지 구간만 잘라 그리는 방식입니다. 서버가 있었다면 LIMIT과 OFFSET으로 필요한 만큼만 조회했을 부분입니다.

내 활동 화면의 세 탭은 코드가 세 벌인가요?

아닙니다. 탭 정보를 객체 하나에 모아두고 화면을 그리는 코드는 한 벌만 씁니다. 탭을 추가하고 싶으면 객체에 항목을 하나 더 넣으면 되고 나머지 코드는 고치지 않습니다.

데이터가 200개인데 렌더링 성능은 괜찮나요?

현재 규모에서는 문제가 없습니다. 목록은 페이지 단위로 잘라 그리고 지도 마커는 선택된 지역만 그립니다. 다만 수천 건으로 늘면 전부 브라우저로 불러오는 구조 자체가 병목이 되기 때문에, 그때는 서버에서 필요한 만큼만 받아오는 방식으로 바꿔야 합니다.

F. 지도 · 외부 API · 비동기 9문항

지도 API를 왜 두 개(Google, Kakao) 썼나요?

탐색 페이지는 국내 도로 기준 길찾기가 필요했고 그 기능을 Kakao Mobility Directions API로 구현했습니다. 지도와 경로 API를 같은 제공사로 맞추는 편이 좌표 처리와 마커 관리가 단순해서 그 페이지는 Kakao Maps를 썼습니다. 메인과 상세는 위치 표시만 하면 되어서 먼저 붙여둔 Google Maps를 유지했습니다.

다만 두 API를 섞은 건 유지보수 관점에서 좋은 선택은 아니었고, 다시 만든다면 Kakao로 통일하겠습니다.

Haversine 공식이 뭔가요? 피타고라스로는 왜 안 되나요?

지구를 구로 두고 두 지점 사이의 최단 거리를 구하는 공식입니다. 위도·경도는 평면 좌표가 아니라 각도라서 그대로 빼서 계산하면 위도에 따라 오차가 커집니다.

경도 1도의 실제 거리는 적도에서 가장 길고 극지방으로 갈수록 짧아지기 때문에, 공식 안에 cos(위도)가 들어가 그 차이를 보정합니다. 지구 반지름은 6371.0088km를 상수로 뒀습니다.

좌표가 없는 식당은 어떻게 처리하나요?

CSV에 지오코딩 상태 컬럼이 있어서 성공이 아니거나 위도·경도가 숫자가 아니면 제외합니다. 거리 계산 중에 예외가 나는 식당도 결과에서 빼고 나머지는 계속 계산합니다. 하나 때문에 전체가 멈추지 않게 하기 위해서입니다.

주변 맛집 정렬은 어떻게 하나요?

반경 안의 식당만 걸러서 거리 오름차순으로 정렬하고 상위 세 개만 자릅니다. 평점 기준으로 바꾸면 평점이 같을 때 리뷰 수, 그것도 같으면 거리 순으로 이어서 비교합니다.

CSV는 어떻게 파싱했나요?

라이브러리 없이 직접 만들었습니다. 한 줄씩 쉼표로 나누되 따옴표 안의 쉼표는 구분자로 보지 않도록 상태를 추적하고, 파일 맨 앞의 BOM 문자를 제거하고, 첫 줄을 헤더로 삼아 각 행을 객체로 만듭니다. 주소에 쉼표가 들어가는 경우가 있어서 단순 split으로는 깨졌습니다.

fetch는 404를 받으면 에러가 나나요?

아닙니다. fetch는 네트워크 자체가 실패했을 때만 예외를 던지고, 404나 500은 정상 응답으로 처리합니다. 그대로 두면 404 에러 페이지의 HTML이 화면에 그려집니다. 그래서 response.ok를 직접 확인해서 아니면 예외를 던지도록 했습니다.

Geolocation 콜백을 왜 Promise로 감쌌나요?

Geolocation API는 성공과 실패를 콜백으로 돌려주는데, 그대로 쓰면 위치를 받은 다음에 할 일이 전부 콜백 안으로 들어가서 코드가 깊어집니다. Promise로 감싸면 await로 평평하게 쓸 수 있고 다른 비동기 작업과 Promise.all로 묶기도 쉽습니다.

await를 왜 두 번 쓰나요?

fetch는 응답 헤더까지만 기다리고 본문은 따로 읽어야 합니다. 그래서 fetch에 한 번, response.text()에 한 번 총 두 번 필요합니다.

API 키는 어떻게 관리했나요?

키를 코드 곳곳에 박지 않고 설정 파일 한 곳에 전역 변수로 모았습니다. 다만 클라이언트 코드라서 브라우저에서는 키가 결국 노출됩니다. 실무에서는 제공사 콘솔에서 사용 도메인을 제한하거나, 서버를 두고 서버가 대신 호출하게 합니다.

G. 보안 8문항

보안 관련해서 고려한 점이 있나요?

세 가지입니다. 로그인 실패 메시지를 나누지 않아 계정 존재 여부가 노출되지 않게 했고, 사용자 입력을 표시할 때 textContent를 써서 HTML로 해석되지 않게 했고, 개인정보 변경에 비밀번호 재확인을 넣었습니다.

다만 근본적으로 클라이언트 검증만으로는 보안이 되지 않습니다.

XSS가 뭔가요? 어떻게 막았나요?

사용자가 입력한 값에 스크립트를 넣어 남의 브라우저에서 실행시키는 공격입니다. 댓글에 img 태그와 onerror 속성을 넣으면 그 페이지를 여는 사람의 쿠키가 공격자 서버로 전송될 수 있습니다.

innerHTML은 문자열을 HTML로 해석하지만 textContent는 글자 그대로만 넣기 때문에, 사용자 입력을 표시하는 자리에는 textContent를 씁니다.

그런데 목록 화면은 innerHTML을 쓰던데요?

맞습니다. 내 활동 목록처럼 innerHTML로 그리는 화면이 아직 남아 있어서 개선이 필요한 부분입니다. 서버가 없어 내 리뷰가 남에게 전달되지 않으니 피해 범위가 자기 자신뿐이지만, 실무라면 치명적입니다.

고치는 방법은 값만 textContent로 넣거나 이스케이프 함수를 만들어 감싸는 것입니다. React나 Vue는 기본적으로 자동 이스케이프합니다.

비밀번호를 평문으로 저장하나요?

네, 지금은 평문입니다. 서버가 없어서 해시 처리를 붙일 자리가 없었습니다. 프로젝트의 명확한 한계로 인지하고 있습니다.

실무라면 BCrypt 같은 단방향 해시로 저장합니다. 해시는 되돌릴 수 없어서 DB가 유출돼도 원래 비밀번호를 알 수 없고, 그래서 비밀번호 찾기가 아니라 재설정만 가능한 것입니다. 저희도 새 비밀번호를 받아 바꾸는 방식이라 방향은 맞습니다.

관리자 아이디가 코드에 있으면 위험하지 않나요?

맞습니다. 이건 진짜 권한 검사가 아니라 화면 분기입니다. 개발자 도구를 열면 우회할 수 있습니다. 서버가 없어서 브라우저가 스스로를 검사하는 구조라 어쩔 수 없었습니다.

실무라면 권한은 DB의 role 컬럼에 두고 서버가 판단하며, 화면의 버튼 숨김은 편의일 뿐 방어선은 서버입니다.

클라이언트에서 검증했는데 서버에서 또 해야 하나요?

네. 클라이언트 검증은 사용자 경험을 위한 것이고 개발자 도구나 Postman 같은 도구로 우회할 수 있습니다. 보안 관점의 진짜 검증은 서버에서 이뤄져야 합니다.

쿠키에 HttpOnly를 쓸 수는 없나요?

쓸 수 없습니다. HttpOnly는 JavaScript가 쿠키를 못 읽게 막는 옵션이라 XSS를 당해도 토큰을 훔칠 수 없게 해 주는데, 서버가 없어서 JS가 직접 쿠키를 만들어야 하는 이 구조에서는 적용할 수 없습니다.

다른 사람이 F12로 데이터를 고치면 어떻게 되나요?

그대로 반영됩니다. 회원 목록도, 관리자 권한도 콘솔에서 바꿀 수 있습니다. 데이터가 브라우저 안에만 있어서 피해는 본인에게만 국한되지만, 이 구조 자체가 신뢰할 수 없다는 점이 서버가 필요한 가장 큰 이유입니다.

H. 협업 · 회고 · 압박 질문 8문항

본인이 맡은 부분은 어디인가요?

인증과 사용자 활동 영역을 담당했습니다. 회원가입과 로그인, 계정 찾기, 개인정보 변경, 그리고 리뷰·댓글·즐겨찾기가 마이페이지로 모이는 부분입니다.

확인 필요실제 담당 범위와 다르면 반드시 본인 기준으로 고쳐서 답하세요. 여기만은 그대로 읽으면 안 됩니다.

본인이 안 짠 코드에 대해 물어보시면

"그 부분은 팀원이 담당했는데, 제가 이해하기로는 ○○ 방식입니다. 정확한 구현은 확인해서 말씀드리겠습니다."

모른다고 끝내지 말고 아는 만큼은 말한 뒤 경계를 밝히는 게 가장 좋은 형태입니다.

가장 어려웠던 점은 무엇인가요?

로그인 상태가 화면 곳곳에 흩어져 있던 문제였습니다. 처음에는 로그인 함수가 헤더도 바꾸고 프로필 메뉴도 바꾸는 식이어서, 화면이 늘어날 때마다 로그인 코드를 고쳐야 했고 한 곳을 빠뜨리면 로그인했는데 로그인 버튼이 남아 있는 버그가 났습니다.

그래서 이벤트로 알리고 각 화면이 스스로 갱신하는 구조로 바꿨습니다.

협업하면서 겪은 문제는?

같은 파일을 동시에 수정하다가 머지 충돌로 작업이 사라진 적이 있습니다. 커밋하지 않은 변경 위에 pull을 받아서 생긴 일이었습니다. 이후로는 작업 단위로 브랜치를 나누고 작은 단위로 자주 커밋했습니다.

이 프로젝트의 한계를 말해 보세요.

일곱 가지로 정리하고 있습니다. 비밀번호 평문 저장, 클라이언트 검증만 존재, 관리자 권한 하드코딩, 시간 기반 ID의 충돌 가능성, 일부 화면의 XSS 취약, 데이터를 전부 브라우저로 불러오는 확장성 문제, 그리고 조합 문자열 키의 순서 의존성입니다.

다시 만든다면 무엇을 바꾸겠습니까?

세 가지입니다. 서버와 DB를 두고 비밀번호를 해시로 저장하며 권한 검사를 서버로 옮기겠습니다. 식당 식별자를 조합 문자열이 아니라 고정된 고유 ID로 바꾸겠습니다. 지도 API를 하나로 통일하겠습니다.

가장 잘했다고 생각하는 부분은?

로그인 상태를 이벤트로 알리고 각 화면이 스스로 갱신하는 구조입니다. 화면이 늘어나도 로그인 코드를 고치지 않아도 되고, 실제로 개발 중에 화면을 추가할 때 그 이점을 확인했습니다.

모르는 것을 물어보셨을 때

"그 부분은 제가 정확히 확인하지 못했습니다. 확인해서 말씀드리겠습니다."

아는 척하다 되물음을 받는 게 최악입니다. 대신 인접한 아는 내용을 한 문장 덧붙이면 대화가 이어집니다. "다만 같은 파일의 ○○ 부분은 이렇게 처리했습니다."

발표 전 체크리스트

전날 · 당일

전날까지

  • API 키 확인 — 현재 js/map-config.js의 Google · Kakao JS · Kakao REST 키가 모두 빈 문자열입니다. 시연할 PC에 실제 키를 넣고 지도가 뜨는지 직접 확인하세요. 이게 안 되면 시연의 절반이 날아갑니다.
  • 실행 환경 확인 — Geolocation은 localhost 또는 HTTPS에서만 동작합니다. file://로 열면 위치 기능과 fetch가 막히니 Live Server로 띄우세요.
  • 시연 계정 준비 — 일반 계정 하나, 관리자 계정 하나. 아이디·비밀번호를 메모지에 적어 노트북 옆에 두세요.
  • 리뷰용 이미지 — 200KB 이하 이미지 한 장을 바탕화면에 올려두기
  • 시연 ⑥번(경로 탐색)만 세 번 리허설 — 가장 실패 확률이 높은 단계
  • 백업 영상 — 시연 전 과정을 미리 화면 녹화. 사고가 나면 이걸 틀고 설명을 이어갑니다.

당일 발표 직전

  • 브라우저 위치 권한 미리 허용 상태로 만들어 두기
  • 브라우저 확대율 125~150% — 뒷자리에서 카드 글씨가 보여야 합니다
  • 알림·메신저 끄기, 북마크바 정리
  • localStorage를 한 번 비우고 기본 데이터만 다시 세팅 — 시연 중 라이브로 만들 리뷰·즐겨찾기 자리는 비워둘 것
  • 브라우저에 메인 페이지를 미리 열어두고 슬라이드 뒤에 대기시키기
  • 슬라이드는 발표자 보기로, 이 대본은 휴대폰이나 태블릿에서 열어두기
마지막으로. 점수가 갈리는 지점은 기능의 개수가 아니라 왜 그렇게 만들었는지를 말할 수 있는가입니다. 쿠키와 localStorage를 나눈 이유, auth:changed를 만든 이유, 이름 대신 아이디를 저장한 이유 — 이 세 가지를 자기 말로 설명할 수 있으면 나머지 질문은 대부분 여기서 파생됩니다.
